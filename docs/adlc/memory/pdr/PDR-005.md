# PDR-005: Kind-A DAG orchestrator reusing factory-mission executor primitives verbatim

## Context

**Problem/Opportunity:**
A rollout is multi-stage, long-lived (24–48h canary windows), gated, and branchy (advance/hold/rollback) — it cannot survive as single-session guidance if the session compacts, the pod crashes, or the human approves 6 hours later. The factory already solved this class of problem four times over (`factory-product`, `factory-architect`, `factory-learn`, `factory-init` are all Kind-A DAGs on one executor contract), so the shape question is whether deploy joins them or invents its own.

**Market Forces:**
* Sibling precedent: `factory-mission` converge loop (DONE/CONTINUE/SPEC_CORRECTION), `factory-review` self-heal loop with maker-checker separation and circuit breaker, `factory-init` layer-tagged correction routing.
* `/ship` is stateless prose — the gap this PDR exists to avoid reproducing.

## Decision

**Decision Statement:**
`factory-deploy` is a Kind-A DAG orchestrator with a fixed stage list — `verify → stage → promote⭐ → canary → expand → full → publish` — running on the shared executor contract (`factory-mission/references/executor.md`) verbatim: step schema, `output_type`s, comment bus markers, lease/heartbeat, worktree isolation, circuit breaker.

**Rationale:**
* A rollout's advance/hold/rollback verdicts fit the DAG correction loop natively; threshold breach → hold/rollback is the same shape as converge → CONTINUE.
* Verbatim reuse (no fork of the contract) keeps one executor to maintain; deploy-specific needs reduce to one addition — environment locks alongside worktrees (two runs must not deploy the same env concurrently).
* Fixed DAG (not declarative graphs) matches all four sibling orchestrators; correction routing bounded by `max_corrections` like the rest of the family.

## Consequences

**Positive:**
* Crash-safe multi-hour rollouts: lease distinguishes live/stale/completed runs; resume works across sessions and runtimes.
* Every stage emits typed outputs (`draft`/`decision`/`findings`/`artifact-ref`) the tracker and `factory-learn` can consume uniformly.

**Negative:**
* Heavier scaffold than a checklist skill; trivial releases must route-classify to a short path or pay DAG overhead.
* Environment locks are new shared state the executor contract doesn't cover yet — first new primitive the family adds.

**Neutral / Acceptance:**
* Output-type discipline per PDR-050: `verify`→`findings`, gates→`decision`, build-ish steps→`artifact-ref`, drafts stay local.

## Alternatives Considered

* **Kind-B control-plane (single-session controller like factory-review/clean)**: lighter. Rejected — multi-hour canary windows with approvals don't fit single-pass control; no resume, no inter-step memory.
* **Leaf checklist skill (no orchestration)**: smallest possible. Rejected — no gate enforcement, no resume, no audit trail; contradicts the factory's guarantees.
* **Fork the executor with deploy-native primitives from day one**: cleaner modeling. Rejected — premature; reuse verbatim first, promote env locks into the contract only after proven need.
