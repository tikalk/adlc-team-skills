# Armed evaluator with scheduled wake-ups, frozen baselines, and unified budget verdicts

## Context and Problem Statement

Canary/expansion steps must evaluate error rate, p95 latency, new JS error types, business metrics, and SLO burn against green/yellow/red bands across 24–48h windows — without holding a worker open, without drifting baselines mid-window, and without consulting the error budget only at gates (where it goes stale exactly when it matters). This is the safety sub-system's computational core. R&W viewpoint: Functional (verdict computation); Concurrency (sleep/wake lifecycle); Information (frozen baseline snapshots as evaluation input).

## Decision Drivers

* No held workers — a 48h window must be waited out, not occupied.
* Reproducible verdicts — "green" must mean green-against-a-recorded-baseline, not green-against-whatever-the-metrics-say-now.
* Budget freshness — burn evaluated with every verdict; gate-only checks decay mid-window.
* Discrete auditability — each verdict is one evaluation event with inputs, bands, and outcome on record.

## Considered Options

* Armed evaluator + scheduled wake-ups + frozen baseline snapshot + unified budget reading
* Blocking stage with heartbeat polling until window elapses
* Externalize evaluation to scheduled CI posting verdict markers

## Decision Outcome

Chosen option: "Armed evaluator with scheduled wake-ups, frozen baselines, and unified budget verdicts", because it is the only option where windows are waited out (not held), verdicts are reproducible (frozen inputs), the budget stays fresh (read per verdict), and the safety brain lives inside the reviewable skill rather than in external automation.

### Consequences

* Good, because zero worker occupancy across multi-day windows; crash between arm and wake loses nothing (state holds thresholds + snapshot + schedule).
* Good, because frozen baseline snapshots make every verdict re-checkable after the fact — "green against this baseline, recorded at arm time."
* Good, because unified budget reading makes canary burn a hold signal inside verdicts (PRD §5), not a stale gate precondition.
* Bad, because wake-ups depend on external cron/scheduler invoking a run-resume command (clarify resolution 2026-10-04, option B) — a missing or misconfigured cron silently stalls the window (mitigation: missed wake surfaces as stale-lease halt on next contact, never silent skip; pre-flight verifies the schedule exists before arming; lease-expiry remains the backstop detector, not the dispatcher).
* Neutral, because evaluator dispatches are idempotent re-computations — a duplicate wake re-records the same verdict rather than double-advancing (guard: program-counter check before acting on a verdict).
* Bad, because metrics-port outages at wake time force hold-and-retry rather than progress (mitigation: bounded retries, then human — absence of data never reads as green).

### Confirmation

Window drill: arm → kill all workers → wake fires → verdict computed against frozen snapshot → correct advance/hold/rollback action; duplicate wake produces no double action; missed wake surfaces as stale-lease halt; metrics outage yields hold, never green.

## Pros and Cons of the Options

### Armed evaluator + wake-ups + frozen baselines + unified budget

* Good, because no held workers + reproducible verdicts + fresh budget + in-skill safety brain.
* Bad, because new wake-up primitive to prove + metrics-outage handling complexity.

### Blocking stage with heartbeat polling

* Good, because no new machinery; single continuous context.
* Bad, because 48h worker occupancy; crash loses polling continuity; wasteful at fleet scale.

### Externalize to scheduled CI markers

* Good, because reuses existing schedulers.
* Bad, because verdict logic becomes unreviewable external automation and the tracker turns from bus into computer — violating the bus-as-memory principle.
