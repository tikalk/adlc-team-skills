# Up-front rule-decided routing with dual-channel outputs and program-counter resume

## Context and Problem Statement

The 8-stage pipeline needs three answers: which route a run takes (full / short-path / halt), how typed outputs travel between stages across sessions, and what resume guarantees after a crash mid-window. Scattering routing across stages makes "why did this run take the short path?" unauditable; a single output channel either strands runs on tracker outages or bloats comments with artifacts. R&W viewpoint: Functional cornerstone (pipeline shape drives gates, audit, resume); Concurrency (program-counter resume semantics).

## Decision Drivers

* Auditability — route choice must be recorded once, in the brief, forever.
* Outage survival — resume must work when the tracker is down (local files) and when the session is gone (comment bus).
* No re-execution — closed stages (a completed merge, a cut tag) must never run twice.
* No honor system — triviality is rule-decided, not self-declared.

## Considered Options

* Up-front classifier recorded in brief + dual-channel outputs (bus markers + run-state files) + program-counter resume
* Per-stage dynamic routing (each stage declares next)
* Bus-only outputs (everything through tracker markers)

## Decision Outcome

Chosen option: "Up-front rule-decided routing with dual-channel outputs and program-counter resume", because it is the mission-identical semantic the team already understands, it keeps one auditable routing decision, and mid-run adaptation belongs in the correction loop (hold → human), not in routing.

### Consequences

* Good, because route classification is a single recorded fact — "why short path?" has exactly one place to look.
* Good, because markers carry decisions/verdicts (small, cross-session) while files carry drafts/previews/records (large, local) — each channel does what it fits.
* Bad, because two channels must stay consistent (marker says advanced, file says held = confusion; mitigation: the program counter in run state is authoritative, markers are the readable projection).
* Neutral, because short-path rule (docs-only / flag-off / patch-with-wide-budget) is encoded in `verify`, not chosen by the invoker.
* Bad, because a run whose risk changes mid-flight cannot re-route (e.g. staging failure can't auto-downgrade; mitigation: correction loop holds for human — deliberate, since re-routing around a human is the failure mode).

### Confirmation

Kill-and-resume drill: run resumes from lease program-counter with zero re-executed closed stages; short-path run's archive names its classification rule and inputs; marker/file consistency check passes per stage transition.

## Pros and Cons of the Options

### Up-front classifier + dual-channel + program-counter resume

* Good, because one auditable routing fact + proven mission semantics + outage-tolerant resume.
* Bad, because dual-channel consistency burden + no mid-run re-routing.

### Per-stage dynamic routing

* Good, because adapts mid-run without humans.
* Bad, because routing logic scattered across 8 stages; adaptation without a human near blast radius is the anti-goal.

### Bus-only outputs

* Good, because single channel, trivially cross-session.
* Bad, because tracker outage strands resume and large artifacts don't fit comments.
