# PDR-010: Deploy monitors its own success only — continuous monitoring belongs to factory-monitor

## Context

**Problem/Opportunity:**
"Monitoring" conflates two jobs: proving this release is healthy (stage verdicts, first-hour checks — bounded, ends) and watching production forever (symptom alerts, runbooks, SLOs — unbounded, never ends). One skill owning both would never finish a run; splitting them late would strand state. With `factory-monitor` planned but unspecified, deploy must draw the boundary now so the handoff exists when the sibling arrives.

**Market Forces:**
* `observability-and-instrumentation` vs `shipping-and-launch` already model the split: instrumentation is built with the feature, launch monitoring rides the release — deploy consumes both, owns neither.
* Sibling scope discipline: `factory-init` explicitly excludes CDRs (owned by `factory-learn`); the sweep ends with a prose handoff recommendation instead of doing the job.

## Decision

**Decision Statement:**
`factory-deploy` owns release-scoped monitoring only — per-step threshold evaluation, first-hour post-launch verification, and a closing handoff packet (metrics endpoints, alert/runbook status, known-unknowns, residual risks); continuous production monitoring is `factory-monitor`'s future scope, consumed via that packet.

**Rationale:**
* A run must terminate: `publish` closes the run with a verdict; an unbounded watch turns every deploy into a permanent process.
* Missing telemetry is a halt-and-route-back-to-build condition (deploy verifies telemetry exists, never instruments — PDR-006 interface rule); similarly, post-handoff production questions route forward to `factory-monitor`, never backward into a closed run.
* The handoff packet mirrors `factory-init`'s hand-off prose pattern, but machine-readable so the future skill can consume it without archaeology.

## Consequences

**Positive:**
* Deploy runs stay bounded and closable; the on-call loop has a named future owner instead of accreting onto deploy by default.
* Handoff packet gives `factory-monitor` its v1 input contract for free.

**Negative:**
* Until `factory-monitor` exists, the packet has no consumer — it lands in the run archive as documentation (acceptable: audit value now, automation value later).
* Boundary disputes possible (is a 48h canary window "release-scoped" or "continuous"?) — resolved by rule: anything the run's verdict depends on is release-scoped.

**Neutral / Acceptance:**
* Symptom-based alerting, runbooks, and SLO tracking from the observability skill are referenced, never reimplemented, by deploy.

## Alternatives Considered

* **Deploy owns continuous monitoring**: one throat to choke. Rejected — runs never close; on-call rotation is an operating model, not a run stage.
* **Deploy does no monitoring (fire-and-forget after flag flip)**: smallest scope. Rejected — abandons the threshold verdicts that justify the whole DAG; `/ship`'s first-hour list exists because this fails.
* **Wait for factory-monitor before specifying deploy**: clean interfaces. Rejected — blocks deploy on an unscheduled skill; the handoff packet lets both sides evolve independently.
