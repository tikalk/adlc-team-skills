# PDR-002: Gated PR merge executor — exact head only, after explicit human gate

## Context

**Problem/Opportunity:**
`factory-review` refuses to merge by design and `factory-mission` defers merges to code-owners, so approved PRs wait on a human to press the button — then the human merges whatever HEAD happens to be, not necessarily the reviewed revision. The merge step is both a toil bottleneck and a correctness hole: nobody verifies the merged SHA equals the reviewed SHA.

**Market Forces:**
* `/ship` assumes merge already happened (its rollout starts at "PR merged to main") — it offers no merge logic to borrow.
* Separation-of-duties precedent: review judges, mission defers; the executor must never grade its own work.

## Decision

**Decision Statement:**
`factory-deploy` may merge a PR only as a gated executor: the exact reviewed head SHA, only when two gates are green — the review-owned Merge Gate (merge-readiness, per `factory-review` rules: code-owner approval or `deploy-ready` label) AND the deploy-owned Deploy Gate (release authorization, any human, identity recorded); if the head moved mid-run, discard evidence and re-verify before merging.

**Rationale:**
* Two gates, two owners, two questions: review answers "is it merge-ready?", deploy answers "shall we ship it?" — deploy never declares merge-readiness itself.
* Preserves maker-checker separation: the humans approve, the agent executes — deploy never reviews its own merge.
* Exact-head rule mirrors `factory-review`'s detached-checkout-at-head-SHA practice, so "reviewed" and "merged" can never silently diverge.
* Optional per run (`--no-merge` for already-merged artifacts) keeps the common deploy path merge-free.

## Consequences

**Positive:**
* Merges become auditable (approved SHA in, merged SHA out, equality asserted).
* Eliminates merge-button toil for agent-driven releases without weakening the human gate.

**Negative:**
* Needs approval-state plumbing against the tracker (comment bus markers or label reads).
* Head-moved restarts add latency on hot branches.

**Neutral / Acceptance:**
* Without gate approval the run halts; deploy never merges on thresholds, timers, or agent judgment.

## Alternatives Considered

* **Always merges whatever is on the branch**: simplest. Rejected — breaks separation of duties and the exact-head guarantee.
* **Never merges (deploy pre-merged artifacts only)**: zero conflict. Rejected — leaves the merge step orphaned; no skill owns it.
* **Merge on green CI without human approval**: fast. Rejected — contradicts the factory's never-auto-merge rule and Merge Gate.
