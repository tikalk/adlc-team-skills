# PDR-008: Defer outcome metrics in v1 — thresholds act as controls

## Context

**Problem/Opportunity:**
A skill without success criteria can't prove it made shipping safer — and the factory's own mission-brief contract demands Goal/Constraints/Success-Criteria for missions. But outcome metrics (rollback rate, post-deploy defects, time-to-rollback) need monitoring plumbing that doesn't exist yet, and `/ship` itself specifies no outcome metrics — only control thresholds. Measuring nothing well beats measuring the wrong things loudly.

**Market Forces:**
* `/ship` controls releases via thresholds (2x error → rollback) without requiring outcome dashboards — the deferral contradicts no upstream.
* The factory tension is real: mission-brief discipline says define success; pragmatism says ship the skill first.

## Decision

**Decision Statement:**
v1 ships with no outcome-metric targets; the green/yellow/red thresholds act as the control system, and the DAG's own advance/hold/rollback counts are available as free exhaust data (no targets attached) for future `factory-learn` mining.

**Rationale:**
* Thresholds already quantify every stage verdict — the release cannot advance on vibes even with zero dashboards.
* Exhaust data costs nothing (the DAG records its verdicts anyway) and keeps the door open without committing to plumbing.
* Explicitly recorded as a decision (not an omission) so the gap is visible and revisit-triggered.
* Aligned with /ship precedent (clarify resolution 2026-10-04): upstream sets no per-item outcome targets — control thresholds with advance/hold/rollback bands + before/after verification checklists + planning-artifact acceptance criteria *are* the success system. Per-PDR metric sections are therefore intentionally absent; the SKILL.md Verification checklist and threshold table carry the standing bar, and each run's brief carries its acceptance criteria.

## Consequences

**Positive:**
* v1 scope stays shippable; no monitoring-plumbing dependency blocks the skill.
* The deferral is traceable — a future metrics PDR supersedes this one rather than rediscovering the gap.

**Negative:**
* Cannot prove the skill made releases safer until metrics land; retrospectives run on anecdotes.
* Risk of permanent deferral ("measure later" often means never) — mitigated by the concrete revisit trigger.

**Neutral / Acceptance:**
* Candidate v1 targets are named but not committed: zero user-reported regressions escaping canary, time-to-rollback <5 minutes (redeploy path).

## Alternatives Considered

* **Full metric set (adoption + outcome)**: every stage measured. Rejected for v1 — needs monitoring plumbing; would block the skill on `factory-monitor`.
* **Outcome-only (rollback rate + defects)**: lighter. Rejected — still needs plumbing; can't attribute improvements to the skill without adoption tracking anyway.
* **Adopt thresholds as the permanent metrics story**: no future work. Rejected — controls are not outcomes; canary-caught vs user-reported ratio is the real safety number and needs its own PDR later.
