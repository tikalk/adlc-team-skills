# PDR-001: factory-deploy as post-merge release orchestrator closing the factory loop

## Context

**Problem/Opportunity:**
The factory outer loop runs intake (`factory-queue`) → execution (`factory-mission`) → review (`factory-review`) → learning (`factory-learn`) — and then stops. The reviewed, merge-ready artifact has no owner for the last mile: nobody stages it, rolls it out gradually, watches the first hour, or rolls it back. Deploys happen manually, unstandardized, and unaudited, so the factory's gate and audit guarantees evaporate exactly where blast radius is largest.

**Market Forces:**
* `addyosmani/agent-skills` `/ship` proves the checklist/threshold/rollback discipline agents need — but ships it as stateless guidance with no gates, resume, or audit trail.
* Factory users already trust hybrid supervision (Intent Gate, clarify gates, Merge Gate); a gateless deploy step would be the weakest link in that chain.

## Decision

**Decision Statement:**
`factory-deploy` is a post-merge release orchestrator: it takes a merged artifact (or an approved head it merges itself per PDR-002) through staging → prod-canary → gradual expansion → full rollout with monitoring and rollback, then hands learnings to `factory-learn`.

**Rationale:**
* Closes the only gap in the queue→mission→review→deploy→learn loop; every other station already exists.
* Post-merge (not pre-merge) positioning preserves `factory-review`'s never-merge invariant and `factory-mission`'s never-auto-merge rule.
* Non-goals are explicit: no infra provisioning, no direct-to-main pushes, no continuous on-call (see PDR-010).

## Consequences

**Positive:**
* Every release inherits gates, dry-run previews, and an audit trail instead of ad-hoc deploys.
* Clear ownership: review judges, deploy executes, monitor watches, learn remembers.

**Negative:**
* One more orchestrator to maintain; teams doing trivial deploys may find the DAG heavyweight (mitigated by route classification — trivial releases take a short path).

**Neutral / Acceptance:**
* `factory-deploy` never approves its own input; without an approved head or artifact ref it halts.

## Alternatives Considered

* **Pre-launch checklist only**: ports `/ship` as a gate before manual deploy. Rejected — leaves rollout/rollback manual, solving half the problem.
* **Full platform provisioner (envs, DNS, infra)**: end-to-end ownership. Rejected — out of scope for a skills repo, blast radius belongs to platform teams.
* **No new skill (fold into factory-mission)**: deploy as mission steps. Rejected — missions end at merge-ready PRs; deploy is a distinct lifecycle with its own gates, windows (24–48h canary), and rollback branches.
