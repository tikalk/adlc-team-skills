# PDR-006: Adopt all six /ship blocks with provider-agnostic flag interface

## Context

**Problem/Opportunity:**
The `/ship` phase (`shipping-and-launch`, `ci-cd-and-automation`, `git-workflow-and-versioning`, `observability-and-instrumentation`, plus deprecation and docs skills) is the best field-tested deploy discipline available to agents — but it arrives as stateless prose. Adopting too little leaves the risky middle (rollout, monitoring, budget) as human toil; adopting it wholesale without factory form loses gates and audit.

**Market Forces:**
* `/ship` principle "Faster is safer" (small batches, frequent releases) must survive gating — gates approve, they don't batch up.
* Tracker-agnostic precedent (`factory-mission/references/tracker-integration.md`): no pinned vendor anywhere in the factory.

## Decision

**Decision Statement:**
`factory-deploy` adopts all six `/ship` blocks reinterpreted as DAG content — pre-launch checklist → `verify`; flag strategy → flag-lifecycle rule; staged rollout + green/yellow/red thresholds → `canary`/`expand` verdicts; monitoring + first-hour verification → stage checks; error-budget gate → release gate; rollback plan → mandatory pre-`stage` artifact — with flags behind a provider-agnostic interface.

**Rationale:**
* The six blocks map 1:1 onto the PDR-005 DAG with no orphans: every `/ship` guarantee lands in exactly one stage.
* Thresholds become mechanical verdicts (error >2x baseline or p95 +50% → rollback; 10–100% / +20–50% → hold) instead of vibes — the DAG can execute them unattended.
* Provider-agnostic flags (generic create/flip/percentage/cleanup interface) keep the factory's no-pinned-vendor stance; concrete providers bind at run configuration.

## Consequences

**Positive:**
* Complete coverage: checklist, flags, rollout, monitoring, budget, rollback — nothing left manual.
* Flag rules (owner + expiry, cleanup ≤2 weeks, no nesting, both states tested in CI) kill the most common flag-debt failure mode by construction.

**Negative:**
* Largest v1 surface of any factory skill; the `verify` checklist (quality, security, perf, a11y, infra, docs) is long — mitigated by reading CI status rather than re-running gates (see interface note below).
* Thresholds assume a baseline exists; first-ever deploys have nothing to compare — `verify` must require baseline establishment or explicit waiver.
* Baseline waiver (clarify resolution 2026-10-04, option A, /ship-aligned): granted by the Deploy Gate approver at checkpoint 1, recorded with reason. The waived run proceeds /ship-style — staging as baseline proxy (full suite + smoke), absolute gates substituting relative ones (health 200, zero new error types, no regression vs staging), flag-OFF prod observation before user impact — and its first canary window doubles as the baseline-establishment run for all later releases.

**Neutral / Acceptance:**
* Interface rule: deploy gates on CI green, never duplicates the `ci-cd` quality-gate pipeline — one owner per pipeline.

## Alternatives Considered

* **Checklist + rollback only (manual rollout)**: smallest shippable. Rejected — leaves canary/monitoring/budget as human toil, the riskiest middle.
* **Rollout engine only (no checklist/docs duties)**: focused. Rejected — deploys unverified code fast, exactly what the checklist prevents.
* **Pin one flag provider for v1**: simpler implementation. Rejected — violates the tracker-agnostic family principle; interface first, bindings later.
