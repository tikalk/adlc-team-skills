# Shared executor verbatim for long-lived rollout runs

## Context and Problem Statement

`factory-deploy` runs multi-day rollouts (24–48h canary windows with human gates between stages) on machinery built for mission-length runs: subagent-per-stage dispatch, lease/heartbeat liveness, comment-bus markers, worktree isolation. The question is whether deploy reuses that runtime verbatim — inheriting crash-safe resume and audit — or builds a dedicated deploy runtime tuned for long windows. R&W viewpoint: Functional cornerstone (runtime shapes gates, audit, resume); Development (one contract to maintain); Concurrency (lease liveness across windows).

## Decision Drivers

* One executor to maintain — a second runtime reimplements lease, bus, and audit badly or twice.
* Crash-safe multi-day windows: sessions compact, pods crash, humans approve hours later; the run must survive all three.
* Family consistency: four sibling orchestrators already run this contract; operators learn one mental model.
* Sibling-identical conventions (heartbeat-renewed standard TTL) over custom long TTLs — renewal, not duration, bridges windows. (Session pin 2026-10-04: no custom 48h TTL; long windows survive by renewal exactly like mission runs.)

## Considered Options

* Shared executor verbatim + additive environment locks
* Dedicated deploy runtime with native window timers
* Hybrid: shared executor for gated actions, timer service for window waits

## Decision Outcome

Chosen option: "Shared executor verbatim + additive environment locks", because only this option preserves a single runtime, single audit trail, and single resume semantic — and the failure modes of the alternatives (divergent audit, split-brain resume across two state homes) are worse than tuning lease renewal for long windows.

### Consequences

* Good, because crash-safe resume, typed outputs, and circuit breaking arrive free and proven.
* Good, because operators and reviewers reason about one executor across all five orchestrators.
* Bad, because lease TTL/heartbeat rhythms tuned for missions must be renewal-disciplined across 48h windows — a liveness bug strands a prod canary in limbo (mitigation: heartbeat renewal continues across windows per sibling convention; external wake-ups re-dispatch evaluation per ADR-005; stale-lease detection halts rather than resumes blindly).
* Neutral, because worktree isolation is heavier than a deploy strictly needs — accepted as the price of zero fork.
* Bad, because environment locks are new shared state the contract doesn't cover — risk of lock contention deadlock (mitigation: locks proven in pilot before any contract promotion; see More Information).

### Confirmation

Integrity suites (`test_playbook_integrity`, `test_generated_artifacts_sync`) stay green; a kill-and-resume drill mid-canary shows zero duplicated flag flips or merges; concurrent same-env runs serialize on the lock.

## Pros and Cons of the Options

### Shared executor verbatim + additive environment locks

* Good, because single runtime, single audit, single resume semantic.
* Good, because four precedents de-risk the mechanics.
* Bad, because long windows stress lease renewal discipline.
* Bad, because worktrees overweight a deploy's isolation needs.

### Dedicated deploy runtime with native window timers

* Good, because purpose-built for long waits; leaner per-stage cost.
* Bad, because a second runtime reimplements lease/bus/audit — the family invariant breaks.

### Hybrid executor + timer service

* Good, because cheap waits without holding workers.
* Bad, because run state and timer state can disagree on crash recovery — split-brain resume.
