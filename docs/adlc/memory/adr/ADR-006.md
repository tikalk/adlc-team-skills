# Idempotent ordered release cut with versioned evidence schema

## Context and Problem Statement

The release cut spans three systems that share no transaction: git (merge + tag), tracker (changelog section), flag provider (cleanup). A crash between tag and changelog must be recoverable without double-tagging or duplicated notes — and the deployment record plus monitor handoff packet must be machine-readable (`deploy-record/1`) so `factory-learn` and the future monitor consume them without parsing prose. Pretending atomicity exists would require building a saga; writing prose would recreate the archaeology the packet was meant to kill. R&W viewpoint: Functional (cut ordering); Information (evidence schema as contract); Development (idempotency-key discipline per step).

## Decision Drivers

* Partial states are inevitable — design for retryable steps, not for their absence.
* Machines consume the record — versioned schema with fixed fields, not markdownkw prose.
* Consumers are decoupled and future — the schema must evolve without breaking readers that haven't updated.
* Curated changelog survives generation — approver edits at preview time (PDR-003), not raw dumps.

## Considered Options

* Ordered cut (merge → tag → changelog → flag-cleanup) with per-step idempotency keys + versioned `deploy-record/1` JSON schema (lenient-additive governance)
* Best-effort ordered cut with free-form markdown record and manual crash recovery
* Single atomic all-or-nothing transaction across git + tracker + flags

## Decision Outcome

Chosen option: "Idempotent ordered cut with versioned evidence schema", because retryability handles the crash case that atomicity fantasizes away, and a versioned schema handles the decoupled-consumer case that prose punts on — both failure modes addressed at design time, neither deferred to incidents.

### Consequences

* Good, because crash between any two cut steps resumes by skipping completed keys — double-tags and duplicated changelog sections become structurally impossible.
* Good, because fixed schema fields (artifact, SHAs, gates + approvers, per-stage verdicts + baselines, rollback rationale, monitor endpoints, alert status, known-unknowns) let `factory-learn` mine and the monitor consume without archaeology.
* Good, because lenient-additive governance (`1.x` + changelog note; breaking `2.0` needs ADR amendment) keeps minor evolution cheap and major evolution deliberate.
* Bad, because idempotency keys per step + schema design + governance are upfront cost before the first pilot (mitigation: keys derive from existing identifiers — SHA, tag-name, content-hash — no new ID scheme).
* Neutral, because cut order is fixed (merge → tag → changelog → cleanup) — reordering later is an ADR amendment, not a config tweak.
* Bad, because SemVer/tag/changelog mechanics assume a cooperative tracker and git host (mitigation: pre-flight checks fail the run before mutation when primitives are unavailable).

### Confirmation

Crash drill: kill between tag and changelog → resume skips tag (key present), writes changelog once; schema validator accepts `1.x` additive fixtures and rejects breaking changes without major bump; consumer test reads a record with an unknown optional field without failing.

## Pros and Cons of the Options

### Idempotent ordered cut + versioned schema

* Good, because safe crash recovery + machine-readable evidence + evolvable contract.
* Bad, because upfront key/schema/governance design cost.

### Best-effort cut + markdown record

* Good, because fastest to build.
* Bad, because crash recovery is manual archaeology and every consumer parses prose differently.

### Single atomic transaction

* Good, because no partial states by construction — in theory.
* Bad, because no distributed transaction exists across these systems; building a saga is strictly heavier than idempotency keys.

## More Information

Cut order rationale: merge first (nothing to tag without it), tag second (immutable point before prose), changelog third (references the tag), flag-cleanup last (dead code removal only safe post-full-rollout). Perspectives for implement: information (schema contract + additive-evolution rule), security (tag signing where the host supports it), evolution (1.x vs 2.0 governance).

## Revisit When

A crash mid-cut duplicates an artifact despite idempotency keys (key design wrong — redesign with incident), or any consumer needs a breaking schema change (mint `deploy-record/2.0` via ADR amendment).
