# Tracker-native gate observation with SHA-bound execution and halt-on-mismatch

## Context and Problem Statement

Two gates authorize the merge: the review-owned Merge Gate (readiness, under review rules) and the deploy-owned Deploy Gate (authorization, any human, checkpoints at promote / canary-expand / merge-execution). Approver and executor may be different agents hours apart, across sessions. The mechanism must let the merge step prove "both green on this exact SHA" without inventing a second auth system — while surviving label races and forged markers. R&W viewpoint: Functional (authorization flow); Security perspective (gate integrity is the security boundary of the whole skill).

## Decision Drivers

* Native UX — humans approve where they already work (approvals, labels, issue markers), not through bot commands.
* Provable conjunction — "both green on this SHA" must be checkable at the merge instant, not just at approval time.
* No second auth system — signed tokens mean building, securing, and explaining parallel infrastructure.
* Forgery response must be a halt, never a judgment call by the potentially-fooled agent.

## Considered Options

* Tracker-native state only (approvals/labels/markers read via TrackerPort)
* Lease-held signed gate tokens minted at approval, SHA-bound, required at merge
* Tracker-native observation + SHA-bound execution-time re-read with halt-on-identity-mismatch

## Decision Outcome

Chosen option: "Tracker-native observation with SHA-bound execution-time re-read and halt-on-identity-mismatch", because it preserves native approval UX, shrinks the race window to the re-read instant, makes the residual risk auditable (re-read values land in the record), and treats forgery as a halt condition consistent with the family rule that gates halt, never degrade.

### Consequences

* Good, because approvers use approvals/labels/markers they already understand — zero new UX.
* Good, because the execution-time re-read + head-equality assertion makes "reviewed ≠ merged" structurally impossible absent a sub-second race.
* Bad, because a residual TOCTOU window (seconds) remains — accepted explicitly, bounded, and logged (mitigation: re-read values recorded; any post-merge SHA drift detected at `canary` arm time aborts the rollout).
* Neutral, because identity-mismatch halts are disruptive by design — a forged marker costs a human investigation, which is the correct price.
* Neutral, because per-repo blackout windows (amendment 2026-10-04, from analyze finding D1) are enforced as Deploy Gate calendar preconditions: a promote/expand/merge checkpoint falling inside a blackout window behaves as an unapproved gate (halt, lease-kept) unless the same explicit-order + recorded-override path as the budget hatch is invoked — blackouts constrain *when*, the budget rule constrains *whether*, and both share one override discipline.
* Bad, because gate state depends on tracker availability at execution time (mitigation: tracker outage = halt, lease-kept, resumable — never proceed on cached gate state).

### Confirmation

Gate drill matrix: both-green merges; either-red refuses with log line; head-moved-between-approval-and-merge triggers re-verification; forged marker (wrong identity) halts with lease intact; tracker outage at merge time halts without acting.

## Pros and Cons of the Options

### Tracker-native + SHA-bound re-read + halt-on-mismatch

* Good, because native UX + structural SHA binding + family-consistent halt behavior.
* Bad, because seconds-scale residual race + tracker-availability dependency at execution.

### Tracker-native state only (no re-read)

* Good, because simplest possible.
* Bad, because label removed after read (or head moved) ships the wrong thing with a green record — the exact failure mode this ADR exists to kill.

### Lease-held signed gate tokens

* Good, because cryptographic proof of both-green-on-SHA; immune to label races.
* Bad, because parallel auth infrastructure to build, secure, and teach — purity at the cost of a second system.
