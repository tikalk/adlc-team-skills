# Independent TrackerPort and FlagPort with reused tracker core

## Context and Problem Statement

Three stages touch flags (canary/expand/full) and three touch the tracker (promote gates, merge, publish). Without a defined seam, each stage hand-rolls provider calls and a vendor switch rewrites the skill. Meanwhile the issue tracker and feature flags are unrelated concerns that must never share an abstraction. R&W viewpoint: Functional (stage contracts); Development (vendor switch = new adapter, zero stage changes).

## Decision Drivers

* No pinned vendors — tracker-agnostic family principle (PDR-006).
* Don't rewrite proven code — mission's tracker-integration layer (markers, labels, lease reads) already works.
* Testability — stages verifiable against in-memory fakes without a live tracker or flag service.
* Separation — tracker and flags meet only in stage logic, never in interface.

## Considered Options

* In-skill ports: `FlagPort` (create/flip/percentage/read/cleanup) + `TrackerPort` (approval-state/label-read/marker-write), bound at run config; mission's tracker layer reused inside the default TrackerPort adapter
* Reuse mission's tracker layer directly + minimal flag adapter beside it (no port boundary)
* Concrete-first: bind GitHub + one flag provider now, abstract later

## Decision Outcome

Chosen option: "In-skill ports with reused tracker core", because it is the only option that keeps stages vendor-free while writing zero new tracker code — the port boundary protects stages, the reused layer protects schedule.

### Consequences

* Good, because a vendor switch adds an adapter without touching any of the 8 stages.
* Good, because in-memory fakes make gate logic unit-testable (approval on/off, label races).
* Bad, because ports expose lowest-common-denominator capability — exotic provider features (cohort targeting) are unreachable by design (mitigation: integer-percent granularity recorded; future binding proposes extensions with evidence).
* Neutral, because the TrackerPort default adapter is a thin wrapper, not a fork — upstream mission changes flow through.
* Bad, because two ports + adapters + fakes are upfront design cost before the first pilot (mitigation: FlagPort is 5 operations; TrackerPort mirrors existing calls 1:1).

### Confirmation

Stage code imports no provider SDKs (grep-verifiable); swapping the FlagPort fake for a stub provider changes no stage file; a second tracker adapter can be added without stage edits.

## Pros and Cons of the Options

### In-skill ports with reused tracker core

* Good, because vendor-free stages + zero tracker rewrite + testable gates.
* Bad, because upfront interface design + lowest-common-denominator ceiling.

### Reuse mission layer directly, no port boundary

* Good, because zero new tracker code of any kind.
* Bad, because issue-centric marker assumptions may fit env-centric deploy runs poorly with no seam to absorb the difference.

### Concrete-first binding

* Good, because fastest pilot.
* Bad, because the abstraction never happens and the second provider forks stage logic — directly contradicting PDR-006.
