# PDR-009: Canary expansion auto-advances on green — human gates only at the three decided points

## Context

**Problem/Opportunity:**
After canary 5% passes, the run must climb 25%→50%→100%. Gating each percentage step would quadruple approval toil and stall 24–48h windows on human latency; advancing blindly would ignore the threshold table. The granularity question is where mechanical verdicts suffice and where humans must re-enter.

**Market Forces:**
* `/ship` rollout: "same monitoring at each step", "advance only if all thresholds pass" — per-step evaluation with no human in the loop; humans appear only as monitors of the first hour, not as per-step approvers.
* PDR-004 already fixed three human gates; this PDR settles everything between them.

## Decision

**Decision Statement:**
Expansion steps (5%→25%→50%→100%) evaluate the threshold table per step and auto-advance on green, hold-and-investigate on yellow, roll back on red; humans re-enter only at the three PDR-004 gates plus any hold/rollback that needs a judgment call (retry vs abort vs spec correction).

**Rationale:**
* Same-as-agent-skills: the thresholds are the decider at expansion granularity; re-asking a human to confirm what green already says adds latency without information.
* Bounded autonomy: yellow/red outcomes route to humans or rollback mechanically — the agent never advances on non-green.
* Consistent with the circuit-breaker family pattern (bounded retries, then human) rather than a new mechanism.

## Consequences

**Positive:**
* Expansion completes in monitoring-window time, not approval-latency time; toil stays at three gates per release regardless of step count.
* Every auto-advance is a recorded verdict (metrics vs thresholds), so the audit trail shows why each step moved.

**Negative:**
* A bad step can auto-advance if thresholds are miscalibrated (e.g. too-lenient latency baseline) — mitigated by baseline-requirement in `verify` (PDR-006) and rollback-on-red.
* Fewer human touchpoints means fewer chances to catch non-metric signals (user complaints, social media) mid-expansion.

**Neutral / Acceptance:**
* Per-step monitoring windows from `/ship` (24–48h canary, same monitoring at each expansion step) still apply — auto-advance shortens nothing, it only removes the approval wait.

## Alternatives Considered

* **Human gate per percentage step**: maximum control. Rejected — approval-latency dominates window time; thresholds already encode the advance decision.
* **Full auto-advance including canary-start**: zero gates mid-run. Rejected — canary-start is a blast-radius boundary (staging→prod); PDR-004 gate stands.
* **Time-based auto-advance (advance after N hours regardless)**: simplest. Rejected — advances on clocks instead of evidence; thresholds exist precisely to prevent this.
