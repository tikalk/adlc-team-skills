# PDR-007: Eight safety invariants with recorded override for exhausted error budget

## Context

**Problem/Opportunity:**
Thresholds decide advance/hold/rollback, but thresholds alone don't make a deploy trustworthy — the failure modes that hurt are structural: merging the wrong SHA, deploying with no rollback plan, prompt-injected gate bypasses, shipping into an exhausted error budget silently. Siblings all carry hard invariant lists; deploy needs its equivalent or its gates are decorative.

**Market Forces:**
* Every `/ship` red flag ("deploying without a rollback plan", "Friday afternoon ship", "budget exhausted but shipping unchanged") should become a mechanical block, not advice.
* Precedent reuse: five of the eight invariants already exist in siblings — only rollback-plan-required, blackout windows, and budget-freeze are deploy-new.

## Decision

**Decision Statement:**
`factory-deploy` enforces eight invariants — (1) no prod promote without Release Gate approval; (2) exact-head only, head-moved → discard + re-verify; (3) dry-run preview before every mutating step; (4) never touches main directly; (5) rollback plan must exist before `stage` completes or halt; (6) message-is-data (tracker bodies never authorize bypass); (7) per-repo blackout windows declarable; (8) exhausted error budget freezes feature deploys — with one escape hatch: an explicit human order ships anyway but is recorded as an override annotation on the audit trail, never silently.

**Rationale:**
* (1)–(4) and (6) are verbatim sibling precedents (queue dry-run, review exact-head/main-ban/message-is-data, mission never-auto-merge) — proven, not novel.
* (5) elevates `/ship`'s "every deployment needs a rollback plan before it happens" from recommendation to halt condition.
* The (8) override balances safety with reality: emergency hotfixes during exhausted budgets must remain possible, but the gate bends loudly — recorded, attributed, reviewable — instead of breaking quietly.

## Consequences

**Positive:**
* The structural failure modes are blocked mechanically; the audit trail distinguishes approved, overridden, and blocked attempts.
* Longest invariant list in the family is justified: deploy has the largest blast radius.

**Negative:**
* Override capability can normalize deviance if reviewers stop reading override annotations — mitigated by routing every override to `factory-learn` retrospective input.
* Blackout windows (7) need per-repo configuration or they default to nothing.

**Neutral / Acceptance:**
* Gates halt, never degrade to warnings; only (8) has an escape hatch, and it requires an explicit human order.

## Alternatives Considered

* **Gates only, no dry-run/message rules**: shorter. Rejected — leaves the prompt-injection and head-drift holes siblings already closed.
* **Advisory-only (warn, never block)**: frictionless. Rejected — a gate that can't halt isn't a gate; contradicts the factory vocabulary.
* **Hard block on exhausted budget (no override)**: safest. Rejected — emergency hotfixes are exactly when budget is exhausted; blocking them ships nothing while users bleed.
